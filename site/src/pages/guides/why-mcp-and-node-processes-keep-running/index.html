Why are node and MCP processes still running after Claude Code or Codex exits?

The short answer

  1. Most MCP servers run as child processes of the agent. Ending a process does not end its children, so something has to shut each server down on the way out.
  2. When that cleanup does not happen, or the server ignores it, the server keeps running. Its parent is gone, so the system adopts it (process 1, launchd on a Mac) and it shows up in Activity Monitor as a plain node, python3 or uvx.
  3. Open bug reports describe this for Claude Code and Codex. A crash, a force quit or a closed terminal can skip the cleanup in any agent.

How an MCP server is started

The Model Context Protocol has a standard way to run a tool server on your own machine, called the stdio transport. The agent launches the server as a subprocess and talks to it through the process's standard input and output. That is why your config holds a command such as npx, uvx, node or docker run -i: the agent runs it for you, once per session or per server.

Each server is therefore one more process, and often several, because a launcher such as npx or uvx starts the real server as its own child.

How it is meant to stop

The protocol says what a well-behaved client does when it is done with a stdio server. The same page gives the order:

  1. The client closes the input stream to the server.
  2. It waits for the server to exit.
  3. If the server does not exit in a reasonable time, it escalates, on macOS typically from SIGTERM to SIGKILL.

It also asks servers to meet the client halfway: they should exit promptly when their standard input is closed, which it calls the primary graceful-shutdown signal. A server that follows this stops by itself the moment its agent goes away, even if the agent never got to send a signal.

Why some keep running anyway

  • The agent never ran its cleanup. If the agent crashes, is force-quit, loses its terminal or is killed, nobody closes the pipe or sends a signal. POSIX is explicit that terminating a process does not directly terminate its children; they are re-parented to a system process and carry on.
  • The agent's cleanup has a gap. That is what the open reports below describe: servers still running after a normal exit.
  • The server does not notice. A Node.js or Python program exits on its own only when nothing is left for it to do. A server that also holds a timer, a socket or child processes of its own can keep running after its input closes, unless its code watches for the end of input and exits.
  • Two processes, one stopped. With a launcher in front, or docker run -i, the thing the agent knows about is the launcher. Stopping only that one can leave the real server, or the container, behind.

What the bug reports say

Our paraphrase of two public reports, both open when we checked on 2 October 2026. We have not reproduced either.

  • anthropics/claude-code#1935: after exiting Claude Code, its MCP server processes can remain running as orphans and accumulate across sessions. The reporter lists Docker-launched, Python and Node servers.
  • openai/codex#25744: a long Codex for macOS session accumulated many helper processes and unreaped zombie children, and the Mac became laggy. This one is different in one way that matters: the parent, the Codex app, was still running.

Other reports of the same kind exist, and some are closed. Which agent versions are affected changes with every release, so check the report for your version.

How to tell a leftover from a live helper

  • Parent process. A leftover's parent process id (PPID) is 1. A helper that still has its agent shows the agent's pid instead. Processes started with nohup, a login item or a service manager also show 1, so on its own it proves nothing.
  • The command line. A package name such as @modelcontextprotocol/server-…, a name starting with mcp-server- or ending in -mcp is a good sign.
  • Age. Started days ago, with no agent session open in that project, is the typical leftover.
  • Zombies are a different thing. A zombie (state Z) is already dead and holds almost nothing; only its parent can clear it. Stopping it does nothing.

What to do about it

Look at them first, then stop them one at a time: how to find and stop leftover MCP servers on a Mac. Before you stop a Node process you did not start yourself, read is it safe to kill orphaned node processes?

To reduce them: exit the agent normally rather than closing the terminal window or force-quitting, remove servers you do not use from its config, and keep the agent up to date. If a server is yours, make it exit when its input closes.
